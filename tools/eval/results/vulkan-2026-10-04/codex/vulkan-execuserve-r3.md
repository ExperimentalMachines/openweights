- **P2 — Catalog remains stale after refusal.** [ModelsScreen.kt:164](~/execuserve/android/app/src/main/kotlin/org/experimentalmachines/execuserve/app/ui/ModelsScreen.kt:164) reads `VulkanSupport.usable`, a plain volatile property that cannot invalidate Compose. Engine status updates recompose installed-model items, while the catalog filter can remain cached. GPU rows stay visible and their Get buttons silently do nothing. **Fix:** expose Vulkan availability as a `StateFlow`, collect it in the screen, and use the collected value when filtering.

- **P2 — Install IDs still collide for identical basenames containing “vulkan.”** [HfCatalog.kt:63](~/execuserve/shared/catalog/src/commonMain/kotlin/org/experimentalmachines/execuserve/catalog/HfCatalog.kt:63): `xnnpack/foo-vulkan.pte` and `vulkan/foo-vulkan.pte` both install as `foo-vulkan`. Downloads share the destination and can overwrite each other. **Fix:** namespace GPU install IDs by backend independently of filename text.

- **P2 — An in-flight pull can enqueue GPU downloads after refusal.** [CatalogRepository.kt:56](~/execuserve/android/app/src/main/kotlin/org/experimentalmachines/execuserve/app/models/CatalogRepository.kt:56) snapshots availability before fetching configs. If inference records a refusal during those requests, the returned GPU variant is still enqueued by `ServeService.pull`. **Fix:** recheck availability immediately before enqueueing in the shared download admission path.

- **P3 — Backend reporting still depends on arbitrary names.** [Routes.kt:549](~/execuserve/shared/server/src/commonMain/kotlin/org/experimentalmachines/execuserve/server/Routes.kt:549) reports any ID containing `vulkan` as GPU, including CPU files; manually installed GPU files with other names report XNNPACK. **Fix:** persist backend metadata in `Manifest`, propagate it through `ModelEntry`, and report that field.
